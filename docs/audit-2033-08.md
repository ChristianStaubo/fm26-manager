# Architecture and workflow audit (in-game August 2033, repo `c82f371`)

An independent, read-only review of the FM26 Moneyball manager: separation of concerns, the
decision mechanisms, the time and improvement loops, human-in-the-loop, fitness for the goal, and
what transfers to other domains.

**Method.** I read the docs you listed, every capability, `game/ui`, `game/screens`, `cli/`, the
bridge's Continue agent, the analysis layer's constants, the tests and the git history (238 commits,
109 since 2026-10-15). I ran `pnpm test`: **165/165 pass in 16.5 s**. I did not run any `fm` command;
that includes read-only ones, because `cli/fm.mjs` appends to the shared `local/runs/commands.jsonl`.
I read the local state files (`decisions.jsonl`, `interventions.jsonl`, `ledger.json`, `deals.json`)
directly to check claims against data.

---

## Executive summary

1. **The method works, and the 4 → 3 → 2 → 1 direction (judgement → screen handler → rule → state
   machine) shows in the code.** The strongest parts are the bounded Continue loop
   with "never retry what may have run", unknown dialogs that are never dismissed, approval
   limits enforced in code, the deals reducer, the reply classifier, `decideSale`, checkpoints as
   data, and the friction → fixture → test loop. Today's stops are new screens, not repeats.
2. **The objective is not measured.** The judge's "net transfer profit" comes from
   `local/runs/ledger.json`, which is typed in by hand from screenshots and ends at **2030/31**, so the
   two seasons the agent played are missing. Nothing tracks profit per player. The **top 4–7**
   constraint isn't in the scoreboard at all: it only checks relegation. As it stands, the system
   can't tell whether its rules make money.
3. **Several money paths fail open.** If the wage cap can't be computed, it becomes **∞**, and so
   does the new wage ceiling. When the daily deals read throws, the error is swallowed and the
   autopilot carries on; in January 2033 that read failed every day. Bids use `setFee` in
   `nearest` mode, so a bid can land up to half a fee step **above the approved maximum**.
   Accepting an outgoing transfer is authorised by a substring search of the decision log.
4. **The rules live in four places and have drifted apart.** They are spread across `PLAYBOOK.md`,
   `policy.json` (with the dated history in the same file), memory files, and constants in code
   (`evaluate_offer.py`, `plan.py`). About 15 policy keys are read by no code, including rules the
   playbook states as hard:
   - at most one Highly Influential player sold per window
   - contract length by age (30+: two years at most)
   - the wonderkid portfolio cap
   - the first-team bar

   Several prose rules contradict the code: the playbook still says "the DoF negotiates", "open at
   value", "pay the release clause" and "CA is never used". The user's rule from 2033-08-05 that
   every window must stay profitable exists only in memory.
5. **The renewal you run and the renewal the report recommends use different tests.** The Savinho
   fix (count the full wage, cap the raise at 25%) is only in `final-year.mjs`, which writes the
   report. `fm renew` and the DoF hand-back still use the old raise-only test, with no raise
   ceiling.
6. **The negotiations are still loops in code, and their state lives on the game screen.**
   `buy.negotiate` has about 10 exits and two reply classifiers. `negotiatePersonalTerms` is 352
   lines mixing maths, clicks and Python subprocesses. If talks are re-entered after a crash, Reset
   restores *our* last offer, and the code then reads it as his demand. Section 2 gives explicit
   machine designs for buying, personal terms and incoming offers.
7. **Local state doesn't follow a save reload, except for deals.** The decision log keeps both
   timelines, and it feeds the counter count, the "paid" floor, the outgoing-transfer
   authorisation, the persuasion-tried check and the judge. Fix it once, centrally, with a timeline
   id on every log entry.
8. **"One operator at a time" is mostly convention.** Only `fm continue` and `fm run` take the lock;
   `holiday`, the cycle's holiday legs, the checkpoint's save, and `buy`/`sell`/`renew`/`click` do
   not. The player agent is kept off `fm approve` by its prompt alone.
9. **The improvement loop leaks:**
   - 49 of the 109 commits since 10-15 touched no test or fixture.
   - Fixtures are single frames, so the holiday, autopilot, bridge and negotiation flows can't be
     replayed.
   - The intervention ledger stops at game date 2033-01-12, though at least seven user corrections
     have come since.
   - Seven supervisor decisions are unreviewed, and two `demote` flags are ignored.
10. **The core transfers to other domains:** rules as data, pure deciders, thin adapters, an outside
    judge with fail/decide/warn, friction → fixture → test, an autonomy ladder with a ledger,
    process reducers with stuck timers, and checkpoints as data. What's FM-specific is the Frida
    bridge, the screen heuristics and the football economics.

## 1. Separation of concerns

The intended layers (rules → decisions → operator → bridge, plus data and CLI) are mostly respected
by the newer code: `decideSale`, `decideLoan`, `decideFinalYear`, `renewalVerdict`, `reduce`
(deals), `classify` (replies) and the checkpoint `STEPS` are pure and tested. The leaks are in the
older, high-traffic flows.

### S1. Capabilities that drive the UI, and one that reaches into the bridge
- **Observation.** `buy.mjs`, `contracts/personal-terms.mjs`, `contracts/renew.mjs`, `buy/ask.mjs`,
  `buy/precontract.mjs` and `sell/list.mjs` mix decisions with screen reading and clicks. Two are
  worse than the rest:
  - `personal-terms.mjs` imports the bridge client directly, skipping `game/ui`.
  - `personal-terms.mjs` also defines an autopilot screen handler inside the capability.
- **Evidence.**
  - Decisions and clicks interleave in `capabilities/buy/buy.mjs:170-255`.
  - `capabilities/contracts/personal-terms.mjs:149` imports the bridge client.
  - The screen handler is `handBackContract` at `personal-terms.mjs:334-351`.
  - Python is spawned during negotiation at `personal-terms.mjs:28-35`.
- **Impact.** These are the flows that cost money, and they're the hardest to test. Only the pure
  helpers (`openingTicks`, `splitTicks`, `wageCeiling`, `lowerPromise`) are unit-tested; the loops
  that call them aren't. Every calibration change (open at 0.85, the release clause as a ceiling,
  wage ceilings) edits a loop that also clicks.
- **Recommendation.** Use a ports-and-adapters split for each flow:
  - `capabilities/<x>/decide.mjs`: a pure `next(context, observation) → action`.
  - `game/screens/<x>.mjs`: reads the screen into an `observation` and executes the `action`.
  - Move `handBackContract` to `game/screens/`.
  - Route the dropdown calls through `game/ui` (a `choose`-style helper already exists).

  This is the same refactor as the state machines in §2.
- **Effort.** M (it falls out of §2's L-sized work).

### S2. Screens that decide
- **Observation.** Several decisions live in screen handlers, and some duplicate a capability with
  different conditions:
  - **The listed-loan rule exists twice.** `decideLoan` accepts if the player is not a starter
    *and* coverage (fee + wage share) ≥ 0.8. The youth-loan handler accepts a listed player if the
    wage share alone is ≥ 0.8, with no starter check and no fee.
  - **The youth loan rule** (the wage-share threshold) is computed inline.
  - **Loan-back** decisions are made in the screen.
  - **The admin handlers carry unwritten rules:**
    - pick the least ambitious board target
    - specialist before physio, never an injection
    - keep the captains
    - keep the collective bonuses
    - decline job interviews

    None of these has a policy key. Two are labelled "supervisor rule, for the user's review" but
    aren't logged as `supervisor-decision`, unlike `youthDecision` and `unwillingWithoutPermit`.
  - **Authorising an outgoing Confirm Transfer** is a loose substring test on any log entry.
- **Evidence.**
  - Listed-loan rule: `game/screens/transfer-offers.mjs:361` vs `capabilities/sell/decide.mjs:101-104`.
  - Youth loan rule: `transfer-offers.mjs:372-384`.
  - Loan-back: `transfer-offers.mjs:388-413`.
  - Admin rules: `game/screens/admin/handlers.mjs:157-206`.
  - Outgoing authorisation: `handlers.mjs:66`, which matches `JSON.stringify(e).includes(player)`
    plus `/accept/` anywhere in the decision, label or action.
- **Impact.** The outgoing check is an irreversible click gated on weak evidence. "Kayode" matches
  any entry that contains the name. A `loan-back` accept, a youth-loan accept, or an entry from an
  abandoned timeline would all authorise a sale. The duplicated loan rules have already diverged.
- **Recommendation.**
  - Authorise outgoing confirmations from the **deals state machine**: a deal for that player,
    `dir: 'out'`, which we moved to `contract`/`confirmation` by our own accept event.
  - Move `youthDecision`, `loanBackWanted` and the listed-loan rule into `sell/decide.mjs`.
  - Give the admin "supervisor rules" policy keys (`policy.admin.*`) and log them as
    `supervisor-decision` until the user has reviewed them.
- **Effort.** S.

### S3. Rules spread over four homes, plus constants in code
- **Observation.**
  - `policy.json` is meant to hold every number, but pricing factors live in Python:
    - `IMPORTANCE` (key starter 1.3 … fringe 0.85)
    - `age_factor` and `contract_factor`
    - `ADD_ON_LIKELIHOOD` (0.4–0.5)
    - `INSTALMENT_DISCOUNT`
    - `WINDOW_CLOSES`, which duplicates `capabilities/season/season.json`
  - `plan.py` hard-codes `DEPTH_MAX = £15M`, while the fm-manager skill tells the model "bench players
    ≤ £8M".
  - `ADD_ON_LIKELIHOOD` contradicts `valuation.addon_weight: 1.0` ("add-ons count at face value"):
    the price book discounts add-ons, but `decideSale` counts them in full.
  - The user's "windows stay profitable" rule (2033-08-05) is only in
    `~/.claude/.../memory/profit-first-depth.md`.
- **Evidence.** `analysis/evaluate_offer.py:36-43, 85-92`; `analysis/plan.py:20-22`;
  `analysis/window.py:55-60`; `.claude/skills/fm-manager/SKILL.md` ("<= £8M"); `policy.json:21-22`.
- **Impact.**
  - Changing the sell multipliers in policy doesn't change how the price book's minimum and target
    are computed.
  - Those two systems multiply: `ourFloor = minimum × 1.1` at `decide.mjs:76`, where the minimum
    already includes `IMPORTANCE` × `age_factor`.
  - Rules in memory are invisible to the cheap player model and to the judge.
- **Recommendation.**
  - Move the decision-relevant constants into `policy.valuation`, `policy.buying.depth_max` and
    so on. Leave pure analysis tuning (`STAT_K`, `MIN_SAMPLE`) in code.
  - Write rules only to policy plus the playbook. Memory should point to them, never hold them.
- **Effort.** M.

### S4. Policy drift: unread keys and stale prose
- **Observation.** No `.mjs` or `.py` file reads these keys (checked with `git grep`):
  - `selling.influential_moves_per_window` and `list_below_hierarchy`
  - `contracts.max_years_by_age`
  - `first_team_bar`
  - `wonderkids.portfolio_max`
  - `buying.replacement_at_least_as_good`
  - `buying.prefer_instalments`
  - `escalate.*`
  - `delegate_to_staff` (it still lists "contract negotiations", though the manager negotiates now)
  - `information.hide_hidden_attributes` (while the final-year matrix, the wage ceiling and the
    wonderkid scan all use CA/PA)
  - `objective.*`
  - `contracts.salary_factors`

  `policy.json:51` still documents core 1.3 / depth 1.0 / surplus 0.9 beside the live 1.5 / 1.2 /
  1.0.

  The prose contradicts the code in several places:
  - `PLAYBOOK.md:118`: open at FM's value (code: 0.85×).
  - `:114-115`: pay the release clause (code: it's a ceiling).
  - `:120`: 2.5× the median (code: 3.0×).
  - `:123`: "the Director of Football negotiates" (code: `negotiator: manager`).
  - `:137-141`: promises "not automated yet" (they are).
  - The fm-manager skill says "`fm renew`: the DoF renews" and "CA is never a ranking".
  - The header of `renew.mjs:1-3` says renewals are delegated.
  - `config/tactic.json` lists Ajer as a starter (released in 2030) and is a 5-2-3, while
    `PLAYBOOK.md:154` says 4-2-3-1.
- **Impact.** The cheap player model reads the playbook and skill first and gets the wrong rules.
  Rules the user believes are enforced (the Highly Influential limit, 30+ contracts at two years)
  aren't. For example, personal terms leave the contract length untouched (`personal-terms.mjs:4-7`),
  so a 31-year-old signing gets whatever length his agent asks for.
- **Recommendation.**
  - Add a **policy lint test**: every non-`_` key must be read somewhere, or be listed in a
    `policy._documentation_only` allow-list.
  - Move dated history out of `policy.json` into `playbook/changes.md`: one entry per rule change
    with the date, the user's words, the old and new value, and the guard test.
  - Then either enforce or delete each unread rule. The three that matter for the goal are the
    Highly Influential limit, contract years by age, and the portfolio cap.
- **Effort.** S for the lint; M to enforce the rules.

### S5. Small duplications that cost correctness
- **Observation.**
  - `offerState` has its own regex set for club replies, beside `replies.mjs`. Only `replyState`
    uses the shared classifier.
  - `finalize` and `makeOffer` are near-copies.
  - Name normalisation is written five times: `deals.key`, `approvals.norm`, `pricebook.key`,
    `audit.norm` and `navigate.fold`/`samePlayer`. `deals.ack` uses a plain `toLowerCase`, so
    accented names miss.
  - Python is run inline with errors swallowed in five places.
- **Evidence.**
  - Reply regexes: `buy.mjs:43-52` vs `capabilities/deals/replies.mjs:8-18`.
  - Near-copies: `buy.mjs:142-161`.
  - `ack`: `capabilities/deals/store.mjs:76`.
  - Inline Python: `store.mjs:30-39`, `renew.mjs:38-43`, `pricebook.mjs:46-50`,
    `personal-terms.mjs:28-35`, `transfer-offers.mjs:295-305`.
- **Recommendation.**
  - Use one `classify` for every GM line.
  - One `names.mjs`.
  - One `facts.mjs` data service, with a cached export read, explicit errors, and fuzzy name
    resolution shared with the screens. Today `wage_bands.py --player` needs an exact name, while
    the hand-back message often gives only a surname, so the wage ceiling is silently skipped.
- **Effort.** S.

## 2. Decision mechanisms

### Where each mechanism is used today

| Mechanism | Where | State |
|---|---|---|
| **State machine (pure reducer)** | Deals: `capabilities/deals/deals.mjs` + `store.mjs` | Good core. Observation-driven, persisted, stuck timers, rewinds on reload |
| **Explicit state set** | Club replies: `deals/replies.mjs` | Good; unknown replies stop at once |
| **Bounded loop with a contract** | `season/continue.mjs` (`requiresExplicitResume`), `season/checkpoint.mjs` (`cycle`, ≤12 legs) | Good |
| **Decision matrix (pure)** | `sell/decide.mjs` (sales, loans, payoffs), `contracts/final-year.mjs`, `contracts/renew.mjs#renewalVerdict`, `free-agents`, `approvals.gate` | Good, tested |
| **Imperative negotiation loop** | `buy/buy.mjs#negotiate`, `contracts/personal-terms.mjs#negotiatePersonalTerms`, `screens/transfer-offers.mjs#incomingOffer` | Next to convert (below) |
| **Imperative loop with hidden state** | `season/autopilot.mjs#run`: 12 mutable flags (`:49`), `lastAction` used for two things (`'press'` at `:110` and the handler loop key at `:165-167`) | Convert to explicit phases |
| **Rule-per-screen table** | `game/screens/admin/handlers.mjs` (already `{name, match, run}`, with a `delegate()` factory) | Nearly declarative |
| **LLM judgement** | After each checkpoint report, the model decides and calls `fm buy/sell/renew` | Free-form; no typed proposals |

### D1. The deals machine: tighten it
- **Observation.**
  - `NEXT` allows nearly every forward jump: `offer` can go to `confirmation`, and `vanished` to
    anything. So `unknown-transition` only catches backward moves.
  - `vanished` has no timeout.
  - A vanished signing counts as completed when his profile shows a "Training" action, which is a
    heuristic.
  - **Errors observing the deals are swallowed** and the loop goes on.
- **Evidence.**
  - `NEXT`: `deals.mjs:12-23`.
  - The "Training" heuristic: `autopilot.mjs:88-96`.
  - The swallow: `autopilot.mjs:99`: `catch (e) { decisions.push({action:'deals-observe', error}) }`.
  - Commit `ec28b96` says the daily Transfer Activity read "failed every day" while the Portal
    rebuilt. On those days the machine built to stop "five agreed signings lapsed unnoticed" was
    blind, and nothing stopped.
- **Recommendation.**
  - Stop after two consecutive failed observations inside a window: fail closed.
  - Give `vanished` a stuck limit.
  - Resolve completions from the export (the contract club) when it's fresher than the event.
  - Narrow `NEXT` per direction (the `in` and `out` paths are drawn in the header comment).
  - Make the machine the one source for "did we agree this?" (S2), and for counters (D4).
- **Effort.** S.

### D2. Buying negotiation as a machine (replaces `negotiate`, `buy.mjs:170-255`)

Context, persisted per target in the deals store (`dir: 'in'`, sub-object `talks`):
`{open, max, approvedLimit, step, releaseClause, fee, round, sellOnTries, keepLoanBack, history[]}`.

```
asked ──unwilling──▶ DROPPED
  │ fee range
priced ──range.low > approvedLimit──▶ NEEDS_APPROVAL
  │ open offer screen (cannot-sign ▶ DROPPED)
editing ──clause ≤ max && fee ≥ clause──▶ PAY_CLAUSE
  │ setFee(atMost, min(fee, max, approvedLimit)); suggest
awaiting_reply ──▶ classify(GM line):
  accepted   ── total ≤ max ─▶ FINALIZE ─▶ FEE_AGREED (hand to the deals machine)
             └─ total > max ─▶ WALK_AWAY
  made/agreement ─────────────▶ FEE_AGREED
  submit ─────────────────────▶ FORMAL_BID ─▶ deals machine
  more   ── clause && fee+step ≥ clause ─▶ PAY_CLAUSE
         ── final offer already made ────▶ WALK_AWAY
         └─ fee := min(fee+step, max) ───▶ editing
  countered ── sell-on present && tries < 2 ─▶ STRIP_SELL_ON ─▶ editing (fee := their up-front, ≤ max)
            ── sell-on kept ─────────────────▶ ESCALATE (no-sell-on rule)
            ── their total ≤ max ────────────▶ ACCEPT_DEMANDS ─▶ FEE_AGREED
            ── final offer already made ─────▶ WALK_AWAY
            └─ fee := next step, or max − add-ons as the final offer ─▶ editing
  rejected  ── clause ≤ max ─▶ PAY_CLAUSE    else ─▶ WALK_AWAY
  unknown / timeout ─▶ ESCALATE (save the TREE, not just the labels)
guards everywhere: round ≤ rounds; every fee set with mode 'atMost'
```

Why: every exit becomes a named terminal state, logged once, and the 0.85×-opening calibration
can be replayed from recorded sequences. It also closes the over-max leak: `setFee` defaults to
`nearest` (`game/ui/controls.mjs:91`), and `buy.mjs:186, 206, 219, 248` call it without a mode, so
a "final offer at max" can land half a step above max (£0.5M at £60M) and be sent via
`makeOffer`/`submit` with no total check. **Effort: L** (M if `bidResponse` and `negotiate` share it
from the start).

### D3. Personal terms as a machine (replaces `negotiatePersonalTerms`, `personal-terms.mjs:181-331`)

Context, persisted per player and deal: `{demand, current, cap, ceiling, limit, tick, method,
offers[], counters[], round, promise}`. **The demand is read once and stored.** Today a re-entry after
our first suggestion presses Reset, which "restores OUR last suggestion" (comment at `:89-90`), and
then reads it as his demand (`:230-231`).

```
entering ── refused ─▶ REFUSED (sell / let run down)
  ├─ promises ── binding position promise ─▶ ESCALATE
  │           └─ lower playing time one step ─▶ form
form ── read demand ONCE (persist) ─▶ gate
gate ── cap/ceiling unknown ─────────────────────▶ ESCALATE   (today: ∞, fail open)
     ── renewal && final-year verdict ≠ renew ─▶ ESCALATE    (one test, see G4)
     ── demand > cap (signing) ──────────────────▶ ESCALATE
     └─ opening ticks (split | percent), never above limit ─▶ suggesting
suggesting ─▶ agent reply:
   Finalize && !counterLine ── salary ≤ limit ─▶ FINALIZE ─▶ AGREED
   accepted-pending ──────────────────────────▶ PENDING
   counter ── round < max ─▶ next ticks (split midpoint | firm/flexible) ─▶ suggesting
           └─ last round ── counter ≤ limit ─▶ FINALIZE   else ─▶ NO_AGREEMENT (talks left open)
   no change in 20 s ─▶ ESCALATE
   payroll / board allowance warning ─▶ ESCALATE (payroll decision)
```

**Effort: L.** It is the most fragile flow (54 personal-terms entries in the log, several outcome
classes), and its money guards depend on subprocesses.

### D4. Incoming offers as a machine (replaces the counter count read from the log)
- **Observation.**
  - The counter count is rebuilt from the decision log by player + club across all time
    (`transfer-offers.mjs:84`). A club that bids again next window gets fewer counters, and after a
    save reload the abandoned timeline's counters count too.
  - Core players are accepted automatically at `sellAt` at any point in the window
    (`decide.mjs:79` with the standing approval at `transfer-offers.mjs:18-19`). The late-window
    logic exists only for listed players.
- **Machine (per bid id = player × club × window):**
  `received → priced{need, sellAt | target/min} → (accept | counter_n | reject | escalate)`.
  Then `counter_n → awaiting_buyer → {accepted → AGREED (deals: out/contract) | countered/final →
  priced with their terms, n+1 | unknown → ESCALATE}`. Guard: **core && daysToClose ≤
  late_window_days → ESCALATE before accepting**, because a replacement is hard to find on deadline
  day (`saleNeedsBuy` stops *after* the sale).
- **Effort.** M.

### D5. The autopilot as explicit phases
- **Observation.** `run()` is a hand-written machine: `advance`, `observe-deals`, `handoff` (press,
  continue-slot, first-continue, match-day, unfamiliar), `required-action` (handler, reopen,
  cleared, none) and stop. Its guards are spread over 12 variables (`autopilot.mjs:49`). Each guard
  was added after an incident (git: `8600199`, `a3a9b73`, `3d8ec72`).
- **Recommendation.** One `phase` variable plus a per-phase guard object (`once per day`,
  `max 3 handoffs`, `same handler + same screen`), and a pure `nextPhase(phase, state, screen)` that
  can be tested with recorded sequences (L3). There's no behaviour change, but the next incident
  becomes a test, not another flag.
- **Effort.** M.

### D6. Admin handlers as a declarative table
- **Observation.** Most admin handlers already reduce to "match on buttons/text → click a label →
  log". Ordering decides ties: `HANDLERS = [...TRANSFER, handBackContract, offersSummary, ...ADMIN]`,
  first match wins (`autopilot.mjs:18, 151`).
- **Recommendation.**
  ```js
  {name: 'injury-specialist', when: {text: / injured$/, buttons: [/^Send To Specialist/]},
   do: {click: /^Send To Specialist/}, rule: 'admin.injury', supervisor: true}
  ```
  Keep code handlers for the multi-step ones (registration, press, persuasion). Add one test that
  runs **every fixture against every handler and asserts at most one match**, instead of
  per-fixture `deepEqual`s. Policy then holds the choices (`admin.injury: specialist|physio`,
  `admin.board_target: least|keep`).
- **Effort.** S–M.

### D7. LLM judgement: give it a typed output
- **Observation.** After a checkpoint the model reads markdown and acts. Its proposals reach the
  user as prose, and `fm approve --proposed N` has to be typed by hand for the ledger to learn
  anything.
- **Recommendation.** Checkpoints emit `proposals.json`. Each entry holds `{id, kind:
  buy|sell|renew|release|precontract, player, price, wage_max, years_max, rule, evidence}`. The user
  approves by id, the executor runs approved ids, and *approved unchanged vs changed* is computed
  automatically. This is the missing link between the judgement layer and the autonomy ledger (H3).
- **Effort.** M.

## 3. The loops

### Time loop: what's solid
- `control()` is a model contract: it is bounded, reports why it stopped, never retries an action
  that may have run, and treats only pre-invocation refusals as retryable (`continue.mjs:47-55`,
  `controls.mjs:1-23`).
- `recover()` never dismisses an unknown dialog (`overlays.mjs:61`). Waits require the
  counterpart's line to *change* (`buy.mjs:123-141`, `personal-terms.mjs:294-300`,
  `transfer-offers.mjs:134-138`).
- The watchdogs (soft at `:67`, hard at `:57-64`), stale-lock takeover (`continue.mjs:62-76`) and
  checkpoint idempotence (`checkpoint.mjs:133-135`) each came from an incident, and each is the
  right fix.

### L1. The lock covers only two commands
- **Observation.** `withLock` wraps only `fm continue` and `fm run`. `ACTING` only checks that
  `fm watch` isn't recording. None of these take the lock:
  - `fm holiday` and `holiday --season`
  - the cycle's holiday legs
  - `fm checkpoint`, which saves the game
  - `fm save`, `buy`, `sell`, `renew`, `precontract`, `click`, `answer`, `register`
- **Evidence.** `cli/fm.mjs:151-153, 173, 181-185`; `checkpoint.mjs:127-152`, where `cycle` takes
  no lock across its legs.
- **Impact.** The rule "one operator at a time" (`CLAUDE.md`) is enforced only between two
  autopilots. Today a second session or a sub-agent can run `fm buy` in the middle of a holiday
  season. This audit had to promise by hand not to act.
- **Recommendation.** Wrap every `ACTING` command in `withLock(cmd)`, have `cycle` hold one lock

## 4. Human in the loop

### H1. The approval schema is too thin for the strategy
- **Observation.**
  - An approval is `{kind, player, limit, note}`, keyed by name only, with no expiry, no window
    and no club (`capabilities/approvals.mjs:22-32`).
  - It caps a **fee** only. Wages, years, signing bonus and agent fee aren't part of it.
  - A pre-contract is gated with `price: 0` (`buy/precontract.mjs:14`). So for **free agents, the
    #1 strategy**, any buy approval authorises a contract whose entire cost is wages and bonuses,
    capped only by the wage ceiling, which fails open (§5 G4).
  - `bidResponse` finds "the approval" by substring over every text on screen
    (`transfer-offers.mjs:201`), so a news line naming another approved player matches.
- **Recommendation.**
  - Make approvals envelopes: `{player, club, window, fee_max, wage_max, years_max, expires,
    note}`.
  - `gate()` checks all of them, and personal terms reads `wage_max`/`years_max`.
  - Resolve the player of a bid response from the headline, via the deals machine.
- **Effort.** S–M.

### H2. Role separation is enforced only by the prompt
- **Observation.** `fm-player.md` says "Never run `fm approve` or `fm intervene`", but the agent
  has the Bash tool and there's no hook or `settings.json`.
- **Recommendation.** Add a `PreToolUse` hook in `.claude/settings.json` that rejects
  `fm (approve|intervene|release|hold|friction resolve)` from the `fm-player` sub-agent. Or
  require an `FM_ROLE=user` environment variable that only the main session sets. That turns a
  promise into a guarantee, which you need before granting more autonomy.
- **Effort.** S.

### H3. The ledger has drifted from reality
- **Observation.**
  - `interventions.jsonl`'s last entry is game date **2033-01-12**.
  - The user corrections since then went into `policy.json` "_" notes, memory and commit messages,
    not the ledger:
    - Savinho's ceiling (2032-07, already absent)
    - Gallardo's sell multipliers (2033-06-24)
    - the Ortega sell-on (2033-07-09)
    - Germany's promise (2033-07-04)
    - the wage cap of 3.0 (2033-06-24)
    - buying cheaper (Ylla, Espino, Mokio, 2033-08-05)
    - windows stay profitable (2033-08-05)
  - `summary()` flags `contracts` and `squad` for **demotion** (corrections with no guard), and
    both are still `auto`.
  - Seven `supervisor-decision`s have never been reviewed (zero `review-agreed` or
    `review-overturned` entries).
- **Evidence.** These figures come from `summary()` over the local ledger: buy streak 0, sell
  streak 1, 6 of 29 corrections unguarded, incoming offers changed in 83% of decisions.
- **Impact.** The autonomy metric under-reports interventions. Promotion and demotion by rule
  aren't happening, so the "earned autonomy" ladder is decorative at the moment.
- **Recommendation.**
  - Make the ledger a side effect, not a chore:
    - every policy change carries a `rule-change` entry with a guard (the lint in S4 can check
      that each dated `_` note has a ledger entry)
    - approvals compute changed vs unchanged from the proposal (D7)
    - `fm audit` returns `decide` items for unreviewed supervisor decisions and for `demote: true`
      capabilities
  - Act on the flags: have `mode()` treat `demote: true` as `approve` until a guard exists.
- **Effort.** S.

### H4. How corrections become rules: the part that works
The pattern is good:
- The user says "rule:" and the session writes a policy number, a pure function, a test, and a
  commit citing the user, the date and the player (37 commit subjects cite the user).
- The renewal backtest is a model of how to discover a rule (`agent-workflow.md` §4).

The weaknesses are where rules land (S3/S4) and the ledger (H3). Record each rule change once in
`playbook/changes.md`, pointing to its policy key and guard test, and keep `policy.json` to current
values.

### H5. Reducing human involvement safely: concrete next steps
1. **Auto envelopes per capability instead of yes/no.** For example, buying turns `auto` when the
   fee ≤ 1.0 × value, age ≤ 25, wage ≤ the ceiling (computed, not ∞), no sell-on, contract years
   within policy, and the window's net spend after the deal ≥ policy (the profit-first rule).
   Anything outside goes to approval. Sales are similar: unlisted, not Highly Influential, not
   core, or ≥ 7 days before the deadline.
2. **Shadow mode.** For one window, compute what `auto` would have done for every approval stop and
   record it beside what the user did. Promote when they agree N times (the ledger already models
   this; it needs the data, D7).
3. **Review supervisor calls in batches** at each checkpoint: list them, then agree or overturn.
   An overturn becomes a rule and a test.
4. **Prerequisites before any of this:** a lock that enforces itself (L1), role guards (H2), money
   paths that fail closed (G4/S1), and an automated scoreboard (G1).

## 5. Fitness for the goal (transfer profit first, balance second, top 4–7)

### G1. The objective isn't computed
- **Observation.** `fm audit` sums `local/runs/ledger.json` (`audit.mjs:57-61, 128`). That file is
  hand-written from screenshots, last edited on 2026-10-15 (real time), and **ends at 2030/31**, so
  the 2031/32 and 2032/33 seasons are missing, including the Ortega, Kislyak, Germany and Gallardo
  sales. No code writes it.
- **Impact.** The one number the whole system optimises is two seasons stale. The overview's
  claims (balance £66M → £126M) come from `results.py`, not from the judge's objective.
- **Recommendation.** Build a **deal ledger** from the deals machine's `completed` transitions plus
  the decision log, with fees and add-ons triggered later as adjustments. Reconcile it against the
  export's club finance (`*_clubs.csv`) at every checkpoint. Then `checkMoney` computes net transfer
  profit for each season and cumulatively.
- **Effort.** M.

### G2. There's no per-player P&L, so rules can't be judged on outcomes
Moneyball's core metric is the return on each player held:

> sale fee − purchase fee − wages paid − agent fees and bonuses − sell-on owed, plus the value
> still held

None of this is computed, so we can't answer "did open-at-0.85 / the wage ceiling / renew-to-sell
make money?" The data exists: 42 `buy`, 39 `incoming-offer` and 54 `personal-terms` entries, plus
the export's wages. Add a `fm pnl` table (player, bought, sold or held, wages to date, P&L, which
rule bought him), and a buy-side counterpart to `sell/negotiations.mjs`: opening ratio vs outcome,
and rounds to agreement. **M.**

### G3. Top 4–7 isn't a constraint, and "the XI at least as good" isn't checked
- **Observation.**
  - The scoreboard checks only relegation (18th) and a warning at 15th (`policy.json:164-173`,
    `audit.mjs:68-72`).
  - The playbook's first principle, "every move must leave the XI at least as good", has no
    computed check.
  - Sales at our price are accepted automatically (a standing approval) at any point in the window,
    and `saleNeedsBuy` stops the autopilot only *after* a core sale (`autopilot.mjs:38-42`).
- **Recommendation.**
  - Add `scoreboard.position_band: [4, 7]`, giving `decide` items when the league position or the
    projected XI falls outside it.
  - Add an **XI-strength metric**: the sum of role scores of the best XI from `manager.py xi`,
    recorded at the start and end of every window, with a judge check that it hasn't dropped
    without a recorded reason.
  - Add the late-window guard for core sales (D4).
- **Effort.** S–M.

## 6. Transferability: what generalises and what is FM-specific

**Generalises (the reusable kit):**
1. **Rules as data, with provenance.** A playbook gives the why and a policy holds the numbers.
   Every change is dated and cites the human's words. Add a schema, a lint and a change log
   (S3/S4).
2. **Pure deciders behind thin adapters.** `decide(observation, policy) → action`. The adapter is
   whatever the domain needs: a browser, an API or a game UI.
3. **Process reducers for long-running work.** States, allowed transitions, stuck timers, a rewind
   when the world resets, and alerts that stop the loop (`deals.mjs`). Hotel bookings, refunds and
   purchase orders are the same shape.
4. **Classify every counterpart reply into an explicit set; unknown means stop and record**
   (`replies.mjs`).
5. **A bounded actor contract**: at most N steps, a stop reason, never retry what may have run, an
   explicit resume (`continue.mjs`).
6. **An outside judge** with `fail` (the tools must change), `decide` (the human's call) and `warn`.
   Every check is something a human once caught.
7. **Friction → fixture → test → resolve**, where the fixture is recorded reality, not invented
   input. Add sequence replay (L3).
8. **An autonomy ladder**: approve/auto per capability, approval envelopes, an intervention ledger,
   and promotion and demotion by rule (H1–H5).
9. **Checkpoints as data.** "Every loop runs every step": the model decides *from* a report and
   never chooses which steps run.
10. **Rule discovery by backtest**, from the human's gut to a principle, a test and an
    out-of-sample check (`backtest_contracts.py`).

**FM-specific:** the Frida/IL2CPP bridge and Unity UI Toolkit quirks, the screen heuristics
(button labels, bounds), the FM Scout export, football valuation (CA/PA, role scores, league
strength), and the transfer-window calendar.

**To make the kit portable:**
- Extract `approvals`, `interventions`, `friction`, the deals reducer (made generic: `process.mjs`),
  `checkpoint` and the judge skeleton into a small domain-agnostic package with no FM imports.
- Make the screen layer a "port" with a fake implementation for tests (L3).
- Write the agent-workflow doc's "Where this lives" as interfaces, not file paths.

The hotel agents would then reuse the loop and supply only adapters, deciders and policy.
